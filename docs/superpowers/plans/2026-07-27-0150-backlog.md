## 2. Make the auto-triage lane fail loudly — DONE, 0.16.0

**Resolved.** `Write(**)` is gone from `--allowedTools`: the CLI rejects it
outright and `Edit(**)` already covered Write, so the rule only ever printed

which is why it survived; it now asserts the valid one is present and the

A run that does not finish now toasts `AUTO-TRIAGE FAILED` with the cause,
names the remedy for the two recurring classes (out of credits, auth), rides
that reason on the pending entry so a missed toast re-surfaces as a failure
rather than a stale stamp, and copies the runner's own stderr into the
report.

**Sharper than the item assumed.** Every trusted outcome silences the manual
toast, so with auto-triage enabled a manual fallback almost always means the
automation did not finish, and the plain "N finding(s)" toast now fires only
under the deliberate `-NoAutoTriage`.

**One innocent case, which an earlier draft of this block denied.** A
`VERDICT: BLOCKED` reply on a CLEAN exit IS a manual fallback, but the agent
read every finding and stopped on purpose: nothing is broken and there is no
runner problem to fix. Recording it as a runner failure would make
`/parallax:drift-triage` report the lane as down, which its own definition of
the `failure` field forbids. It therefore carries no failure reason and gets
its own toast instead. Caught by the whole-branch reviewer, which noticed the
code comment saying "the designed path, not a broken runner" sitting directly
above the line that set the failure anyway.

**The clean exit is load-bearing, and the first fix omitted it.** A crashed
or killed run that happens to print a BLOCKED line before dying is NOT a
deliberate handoff. The first version of this fix keyed on the verdict text
alone, so a nonzero-exit crash was classified as an intentional stop and
recorded an empty failure — telling a triage session the automation finished
on purpose when it had died. The cross-vendor lane found that inside the fix
for the reviewer's finding, which is the same fix-contains-a-defect pattern
this project keeps hitting. BLOCKED now requires `$agentExit -eq 0`, with its
own state-machine scenario.

Three state-machine scenarios added: `credits-death` reproduces the
2026-07-21 death exactly, `failure-resurfaces` proves a missed failure toast
re-surfaces, and `blocked-crash` proves a BLOCKED line on a nonzero exit
reports as a runner failure. The pre-existing `no-verdict` scenario gained an
assertion rather than being added; the backup reviewer lane caught this
enumeration naming it as new. Full suite: ALL SCENARIOS PASS.

**Problem.** The headless drift auto-triage is the unattended safety net.
It can die and leave no signal.

**Evidence.** The 2026-07-21 run exited 1 on `You're out of usage

**Two parts.** Fix the wrong permission rule in the runner's

## 6. The backup lane's evidence rule breaks under concurrent sessions — DONE, 0.16.0

**The residual question is ANSWERED YES, 0.18.0.** The last candidate below
asked whether kimi can be pointed at a per-session log file, which would
remove the shared-stream problem at the root. On `kimi-code` it can, and it
does so by default: every session writes its OWN
`sessions/wd_<workspace>/<session-id>/logs/kimi-code.log` and its own
`agents/main/wire.jsonl`. There is no shared stream and nothing to attribute
by position, so the collision this item was raised for cannot occur between
debates at all. That is also why the lane lock was deleted (item 16) — the
window it protected no longer exists. Measured live 2026-07-31; see
`rounds/2026-07-31-kimi-code-swap/kimi-live-debate-record.md`.

**Resolved with both candidate fixes, not one.**

**What blocked the obvious fix.** Candidate 1 said "bind the round to the
session id the CLI prints". The three evidence lines carry NO session id:
their session field is empty, and only later runtime lines are stamped. So
matching an id on the evidence line is impossible.

**What replaced it.** Bind by ORDER. `Created new session: <id>` and
`Resuming session: <id>` DO carry the id and sit immediately before that
session's three lines, so the rule reads only from this round's session
event up to the next event of any id, and requires exactly one of each
inside that block. Foreign session events are ignored rather than counted.
The block's kind is checked too, which catches a resume that silently
started fresh.

**Verified on live data, not reasoned.** A concurrent kimi session was
running in another project during this work. Over a 17583-byte window
holding two foreign startup blocks, the old whole-window rule reported two
of each line and failed; block attribution resolved both sessions to
exactly one of each. That is the 2026-07-27 failure reproduced and then
fixed, on the real log.

**Plus the lock.** Ordering cannot stop parallax colliding with itself, so
`tools/kimi-lane-lock.ps1` serializes this plugin's own dispatches. It is
advisory and age-bounded: no PID is recorded, because the holder is a driver
agent whose shell invocations are each short-lived, so a recorded PID would
read as dead immediately and every lock would look stale. 41 tests cover it,
including that breaking a stale lock is never silent and that a malformed
lock cannot wedge the lane.

**What the lock does and does not guarantee**, narrowed THREE TIMES after the
cross-vendor lane refuted the broader claims this block first made. Each
round's fix contained the next round's defect — three rounds running — so the
wording below is what survived being attacked, not what was drafted:

- The label is the ownership credential. A NONBLANK one is required on
  acquire, so this script never writes a lock without one. It can still read
  a lock written by hand or by an older version, and a release without
  `-Force` refuses those too: an unusable `label` field means no credential
  exists to present. Round 1 claimed "an unlabelled lock cannot exist",
  which was false — `label: 0`, `label: null` and a missing label are all
  falsy, and each was freed by a bare release until round 2.
- Ownership is a case-sensitive STRING MATCH and nothing more. Two callers
  passing the same label are indistinguishable, so either can release the
  other's lane. The contract requires a label unique to the round; the
  script cannot enforce that and does not pretend to.
- The 45-minute staleness threshold is a constant with no override of any
  kind. Two earlier shapes were both lock-stealing: a `-MaxAgeMinutes`
  parameter, so `-Acquire -MaxAgeMinutes 0` broke a fresh lock with no
  `-Force` — demonstrated by this suite's own stale-lock test; then an env
  override honoured "whenever the lock path is redirected", which gated on
  the redirect being PRESENT rather than on it differing from the default.
  Round 1 claimed that seam "cannot be aimed at the real per-user lane".
  It could: setting the redirect to the exact default path stole the real
  lane, reproduced by running it. Tests now backdate their own temporary
  lock instead of asking the script to lower its guard.
- A stamp in the FUTURE used to produce a negative age that never reached the
  stale branch, so the lane stayed busy until the clock caught up and status
  printed "held -360 min" to a human. A future stamp now reads as unusable
  and is breakable.
- Age depends on the INSTANT, not on how the instant was written down. Round
  3 found that it did not: `[datetime]` parsing converted an offset-bearing
  stamp to local time but left a terminal `Z` as UTC, and subtracting two
  `[datetime]` values ignores that difference. On a UTC-05:00 machine a
  CURRENT `Z` stamp therefore read as 300 minutes in the future and was
  broken on sight, while a five-hour-old `Z` stamp read as brand new and held
  the lane past any threshold. Both reproduced by running them. Parsing is
  now offset-aware, and a test asserts the same instant in three
  representations reads the same age.
- A stamp that is not a string — an object, an array, a number — used to
  reach the parser with no matching overload and THROW, which killed the age
  routine before it could return the infinite age it was written to return.
  The lock then read as "held 0 min" and never aged, so the routine that
  exists to stop a malformed lock wedging the lane was itself the wedge, and
  only `-Force` could clear it. Non-string stamps are now unusable and
  breakable, and this block's claim that "a malformed lock cannot wedge the
  lane" is true for the first time.
- An age that cannot be true is described, never printed. Two shapes reached
  a human as measurements: "held -360 min", and "broke a stale lock,
  1.79769313486232E+308 min old" from the sentinel value. Both now read
  "age unusable".
- Residual, real: a LIVE round still running past 45 minutes becomes
  breakable, because nothing checks liveness. Rounds take minutes, so the
  margin is wide, but this is not impossible.
- Residual, documented at the write site: acquire is last-writer-wins, so
  this narrows a minutes-wide race to a milliseconds-wide one rather than
  closing it.

**Residual, pinned in the contract:** a foreign session starting INSIDE this
round's sub-second startup block still truncates it and still fails the
round. Collisions are rare now, not impossible. The "exactly one" rule was
never relaxed, per the item's constraint.

**Original problem, for the record:**

**What happened.** On 2026-07-27, round 1 of the 0.15.0 plan debate was
discarded unread under the route-attribution rule. Two calls wrote route
lines into one measurement window: this session's dispatch at 16:08:44

**The rule worked. What it caught was not a threat.** The reply was
almost certainly the right one. Containment held on evidence that does
not depend on the log: no marker file, empty mirror delta, exact tool
allowlist. What failed was attribution, because two calls in one window
make the log unable to say which lines are whose.

**The gap.** `~/.kimi/logs/kimi.log` is user-global. The offset rule
assumes one session at a time on the machine, and says so nowhere. A

evidence, and no way to tell a collision from a real misroute after the

**Constraint that must survive any fix.** Do not relax the "exactly one"
rule. It is what makes the evidence mean anything. The fix must make
collisions rarer or distinguishable, not tolerated.

**Shape of a fix, not decided.** Candidates:

- Bind the round to the session id the CLI prints, so attribution comes
  from the reply's own identity rather than from position in a shared
  file, with the offset rule kept as the containment check.
- Take a lock for the duration of a dispatch, so two parallax debates on

- Detect the collision before spending the call: capture the offset,

## 7. The reviewer's TOOL surface is unmeasured - DONE, 0.24.0

**Problem.** 0.17.0 measures the reviewer's PROMPT: a clean result means
no skill is advertised, no plugin or apps block is present, and nothing
inside the reviewed tree is instructing the reviewer. Tools are not in
the prompt. An MCP server and the memories feature both reach the
reviewer without appearing anywhere the probe can read, so a run can
satisfy every rule above while the auditor holds a code execution tool
and a cross-session memory store.

**Evidence, observed 2026-07-28 during the 0.17.0 behavioral run.** A
review round dispatched with `--sandbox read-only --disable plugins
--disable apps` and the verified skill-disable override logged three
`mcp: node_repl/js started` lines in codex's own transcript. The machine
config carries `[mcp_servers.node_repl]`, `[windows] sandbox = "elevated"`,
`[features] memories = true`, and `[memories] use_memories = true`. The
run also lost two behavioral cases: `diff-mode-spec-fidelity` timed out
with the round still running, and `no-manufactured-objections` kept an
uncited correction.

**Why the 0.17.0 mechanism cannot be reused.** `codex debug prompt-input`
renders prompt text and calls no model, which is what makes it free. It
does not render the tool list: measured the same day, the rendered prompt
mentions neither `node_repl` nor memories anywhere. `codex debug` has only
`models`, `app-server` and `prompt-input`, so there is no free tool-list
view to measure against. A design that verifies a tool removal needs a new
source of evidence, not a second call to this one.

**What is known about the levers, and what is not.** `--disable memories`
is accepted (exit 0), unlike `--disable skills` which errors with
`Unknown feature flag: skills`. `-c mcp_servers={}` parses. NEITHER is
verified to actually remove the tool, because nothing free proves it. Do
not ship either as a control on the strength of parsing alone: that is the
exact false-clean the 0.17.0 probe exists to forbid.

**Constraint that must survive any fix.** Same as 0.17.0's. An unmade or
unreadable measurement is never a clean one, and a lever whose effect is
unverified is a mitigation, not a control.

**Shape of a fix, not decided.** Candidates:

- Find a surface that names the resolved tool list, and measure it the way
  the prompt is measured today.
- Detect the failure after the fact instead: parse the round transcript
  for `mcp:` lines and treat any as a transport failure, which is weaker
  because it spends the call first.
- Route the review through a codex home that carries no MCP servers and no
  memories, which reopens the credential problem 0.17.0 deliberately
  avoided.

**The second row is the finding.** When the quoted span contains no space, the
argument count does not change, so nothing fails. The dispatch succeeds, the
route header verifies, the reply comes back, and the reviewer has read a brief
this side never wrote. In a tool whose entire value is that both sides argue
over the SAME evidence, that is a transport that edits the evidence and reports
success. It is the same shape as this repo's governing rule: an altered brief
must never look like an intact one.

The first row is the loud failure the field report hit: exit 2 with
`error: unexpected argument`, which reads like a malformed command, so the
first instinct is to rewrite a dispatch that was correct.

**This refines the field report's mechanism, which named the npm wrapper alone.**
The wrapper is the vehicle; the HOST is the discriminator. That also explains why
the 0.20.0 mode-diff debate ran four resumes with quoted briefs and never saw it:
those went through PowerShell 7. It is the same class as 0.16.0's lane lock,
which did not lock on PowerShell 7 at all and passed a green suite on 5.1.

**The fix, probed by the field report against a live session: use stdin, exactly
as round 1 does.**

```
Get-Content -Raw <brief-file> | codex exec ... resume <SESSION_ID> - > <transcript> 2>&1
```

That run returned exit 0, resumed the correct session, and passed quotes through
untouched. Both dispatches then look identical, which is also easier to read.
One occurrence in `SKILL.md`; no other skill, command or agent file carries it.

**Do NOT ship the sanitize workaround** the field report used mid-run
(`-replace '"', "'"`). It works and it quietly alters the brief, which is the
defect, not the fix.

**Priority.** Highest of the open items. It fires on round 2 of any debate whose
brief quotes anything, which is most of them, and on 5.1 it can fire without
saying so.

## 22. No documented flow for refreshing the mirror when HEAD moves — DONE, 0.21.0

**DONE, 0.21.0.** `a602b55`, plus `3dcde79` for the manifest read-failure
and both test seams after the whole-branch review.

**Evidence.** Thirteen cases, including both positive controls. The
finding that shaped the release: the frozen plan chose to compare the
source's STATUS OUTPUT to detect an edit to an untracked or ignored
review input, and that does not work - `git status` reports the path,
not its bytes, so editing an already-ignored file leaves the capture
byte-identical. Measured 2026-08-04, found because the oracle for that
exact case passed when it should have failed. The fingerprint now covers
the status capture AND the content of every path status names.

**NOT covered.** The two-HEAD gate proves committed-HEAD freshness only.
Non-HEAD inputs are bound at CONSTRUCTION time and post-construction
drift is caught by the fingerprint, which is a different mechanism with
a different failure mode. Nothing detects a change made between the
verify call and the dispatch that follows it; the window is the driver's
to keep short. The gate is also not authentication: it detects change,
never intent.

Two more the mode-diff debate named, both real and both left open on
purpose. The bridge compares ENDPOINTS, so a source that moves away and
back during the copy satisfies the head equality and the fingerprint
equality alike, while the copied worktree can still hold intermediate
bytes. And the path budget is measured before the mirror root exists
while robocopy runs after, so a path created in that window is in the
copy's universe and not in the measured one. Both close only by
constructing from an immutable filesystem snapshot, which is a design
this release does not attempt; the contract regions now state the
endpoint and as-enumerated limits rather than implying the stronger
guarantee.

Round 2 added a third. The fingerprint covers the status capture and the
content of the paths that capture NAMES, so a tracked file git calls
CLEAN is in neither. A raw-byte change that survives the clean filter
unchanged therefore moves neither HEAD nor the fingerprint: the autocrlf
case this file already documents is the mild version, and a
content-stripping filter is the severe one. Post-construction drift
detection is limited to what status can see, and the region now says so.

Raised 2026-08-03, field report §3.

**Problem.** Mode diff's normal shape is review, apply fixes, re-review, so HEAD
moves every round and the mirror built for round 1 is stale for round 2. Neither
`SKILL.md` nor `references/backup-lane.md` says so; the mirror is described as a
construction step, singular. The field report built seven mirrors by hand, one
per round, each a full re-copy plus a fresh probe.

**Why it matters.** Resume against a stale mirror and the reviewer confidently
reviews code you already changed. Nothing catches it: the route header verifies
the REVIEWER, not the TREE. That is an unmade measurement wearing a clean
result.

**Shape of a fix, not decided.** A `-Refresh` switch that re-syncs an existing
mirror and re-runs the probe would cut most of the cost. At minimum, one line
saying to rebuild at the new head before every round that follows an applied
fix, and to state the head in the brief so a stale tree is at least visible to
the reviewer. The field report did the latter by hand and calls it a workaround,
not a control, which is the right reading.

**Priority.** Above item 15. The silent-failure mode is real and the workaround
depends on an operator remembering.

## 24. The round cap measures the wrong thing in a fix-verify loop — CLOSED 0.22.0

Raised 2026-08-03, field report §5.

**Problem.** `debate-protocol.md:53` caps the default at 4 exchanges, framed as
the signal to stop spending tokens on an argument evidence has not settled. That
framing fits a CONTESTED debate. It does not fit a fix-verify loop, where every
round finds something new, the session verifies and accepts it, and nothing is
ever argued.

**Evidence, from two independent runs.** The field report ran 8 rounds with zero
refutations, zero escalations and zero repeat findings; stopping at 4 would have
shipped its defects 5 and 6. The 0.20.0 mode-diff gate ran 5 rounds with finding
counts 6, 5, 2, 1, 0 and only converged because the count reached zero.

**The two regimes share one counter.**

- **Contested**: the same point argued across rounds. A cap is exactly right;
  more rounds will not settle it and the user must.
- **Fix-verify**: each round finds something new and it is accepted. The real
  signal is a round that finds nothing new, which is the loop-until-dry shape.

**Shape of a fix, not decided.** Something like: the cap counts rounds with
CONTESTED points; a round that ends in accepted findings resets it; the debate
ends when a round produces no new accepted finding. Otherwise an honest operator
either stops early or silently overruns, and both runs above overran.

**CLOSED 0.22.0.** The cap now counts **4 CONSECUTIVE CONTESTED exchanges**,
and a round whose findings are all accepted RESETS it to zero. A separate
caller-set TOTAL FIX-VERIFY BUDGET bounds the other regime and, when exhausted,
PAUSES for the user's authorization instead of certifying - because the session
both adjudicates whether a finding is accepted and decides when to stop, which
is one actor holding both roles.

The termination predicate this item sketched was LOGICALLY WRONG and was
replaced rather than adopted: "the debate ends when a round produces no new
accepted finding" also ends a round whose only new finding is CONTESTED, the
exact case the cap exists to escalate. The rule is now an ADJUDICATED DRY ROUND
- no new substantive finding AND no outstanding contested point.

Both overrun runs are named in the shipped text so the rule cannot be rewritten
without confronting them. The 0.21.1 seven-round account is no longer prose:
its twelve round records are retained under
`docs/superpowers/plans/rounds/2026-08-04-transport-and-mirror/`. The 0.20.0
`6,5,2,1,0` sequence is still NOT retained anywhere and remains an assertion.

**Priority, as filed.** Below 20 and 21. It changes a documented default, so it
wants a plan debate rather than an edit.

## 25. No scope guidance for pre-existing defects a diff review walks past — CLOSED 0.22.0

Raised 2026-08-03, field report §6.

**Problem.** Mode diff tells both sides to judge spec fidelity, port fidelity,
correctness and internal consistency. It says nothing about SCOPE. In the field
report's run, rounds 4 through 7 all landed on defects that PREDATE the range —
bugs in adjacent code the diff happened to walk past, one traced with `git log
-S` to a much earlier branch.

**Why it needs an answer in the docs.** The tension is real in both directions:
surgical-changes discipline says leave it; certifying a module you know is broken
says fix it. Either answer is defensible. Having NO answer means each session
improvises, and the attestation record then means slightly different things run
to run — which is the one thing an attestation cannot afford.

**What was improvised, and it worked.** Mid-debate the session declared a policy
to the reviewer in the round-6 brief: fix pre-existing defects that are the same
class as what the branch is already fixing AND live on the surface the smoke pass
will exercise; record anything else for a follow-up branch. The reviewer accepted
it, and on the next finding offered a formulation the skill could adopt outright:
it "can be a separate follow-up commit, but I would not certify the module before
that follow-up lands".

**CLOSED 0.22.0.** The improvised rule is adopted, with the two judgement calls
turned into operational definitions, in `references/debate-protocol.md`:

- **SAME CLASS** is a violation of the same NAMED invariant, contract clause or
  frozen postcondition, cited by name. Not similar symptoms, not the same file,
  not the same subsystem.
- **VERIFICATION SURFACE** is the exact files, symbols, runtime paths and gates
  ENUMERATED BEFORE the finding is raised. Enumerated after, it is a surface
  drawn around the answer someone already wanted.
- **The certification unit** is named before the debate ends rather than
  inferred from what was touched.
- **An exercised surface with an outstanding follow-up cannot be attested**:
  FIX, ESCALATE, or an explicitly narrowed claim naming what is excluded. The
  reviewer's own formulation, adopted.

**Priority, as filed.** Lowest of the new items, and the least mechanical. It is
a policy question, so it belongs in a plan debate with the round-cap item.

## Item 26: release the kimi lane when a debate ends — PARTIALLY CLOSED 0.22.0

**Filed 2026-08-03, from a live incident, not a review.** Two sessions on this
machine blocked on the lane lock for over three hours. The lock behaved
correctly at every step; the DEBATE did not release it.

**What happened.** This session took the lane lock for the 0.21.0 plan debate
(`debateId 2fd4bc9a...`, debate home under the session scratchpad), finished
the debate, froze the plan, and moved on to build work. The lock stayed held
for the life of the session process. A second session in another repo needed
the lane, measured the holder as genuinely LIVE, and correctly refused to
break it. It stayed blocked until the holder released by hand.

**Why the lock is not the defect.** `backup-lane.md`'s `lane-lock` region is
explicit that staleness is LIVENESS and never a clock, because a predecessor
expired holders by AGE and that let anyone break a live round that ran long.
Adding a timeout here would reintroduce exactly that fault. The refusal was
right. The holder was wrong.

**Where the gap actually is.** The only documented release is a SIDE EFFECT of
teardown: `new-kimi-lane-home.ps1 -Remove ... -Nonce <nonce>` "releases it only
after the home is gone", stated inside the `lane-lock-call-lifecycle` region.
There is no named "the debate is over, release the lane" step anywhere a driver
reads at debate end, and nothing detects a debate that finished without one.

**`/parallax:doctor` will not catch it, by design.** Check 8 maps `held` plus
LIVE to OK and says LIVE "never means a debate was abandoned". That is the
right rule for reclaim rights and the wrong outcome for visibility: a forgotten
teardown is indistinguishable from an active review.

**Two changes, one item.**

1. **Make teardown a named step at debate end** in the backup-lane flow, not a
   clause inside the lifecycle contract. A driver reading the debate's closing
   steps must see it.
2. **Have the doctor report a quiet live holder as INFORMATION.** When a held,
   live record's debate home has had no file modified for some interval, say
   so in the detail text. It must change NOTHING about who may reclaim, and it
   must not move the row's verdict off OK, or it becomes the age-based expiry
   the design already rejected.

**Scope note.** Change 2 needs a rule for what "quiet" reads from, and it must
degrade to silence when the debate home is unreadable or already gone: an
unmeasurable idle time is not an idle debate.

**A SECOND, MORE SEVERE DEFECT, reported the same evening by the KitnEssentials
session and partly measured here.** `tools/kimi-lane-lock.ps1 -ResolveOwner`
returned a DIFFERENT process id on each call under that harness, so the lock
recorded an owner that read as DEAD almost immediately and the normal teardown
could not release it. That session fell back to the guarded force path.

**The mechanism, measured here 2026-08-03.** `-ResolveOwner` returns the DIRECT
PARENT of the PowerShell process running the script and nothing else. On this
machine that parent IS the long-lived `claude.exe` session process, and four
consecutive calls returned the identical pid and start ticks, so this harness
cannot reproduce the instability. Under any harness that inserts a wrapper
between the session process and PowerShell, the parent is that intermediate,
which exits when the command does.

**Why this is worse than the teardown gap.** A recorded owner that is already
dead makes the lock RECLAIMABLE BY ANYONE at the next acquire. The mutual
exclusion the lock exists to provide is then gone, and two debates can run
against one credential while every status read looks ordinary. The stuck-lock
symptom is the visible half; this is the silent half.

**What the contract already says, and why it is not enough.** The
`lane-lock-call-lifecycle` region states that ownership is resolved ONCE per
debate and passed explicitly, precisely because "deriving it from the invoking
shell's parent is correct only for a DIRECT invocation, and under any wrapper it
names an intermediate process that also exits". The tool implements exactly the
resolution the contract warns about, and nothing verifies the requirement holds.
A caller who re-resolves at teardown then cannot match the recorded identity
and cannot release.

**CORRECTION, 2026-08-04 (0.22.0 plan debate, confirmed independently).** The
clause that used to sit here - "which the doctor's own recovery command does" -
was a MISREADING and is struck. The doctor's `-ResolveOwner` use is the LANE
LOGIN recovery command, printed for an absent, unreadable or malformed
credential: it creates a fresh debate id, acquires with the freshly resolved
identity, and releases the SAME identity in its own `finally`
(`tools/new-kimi-lane-login.ps1:521-574`). That is a self-contained login-lock
lifecycle, not a teardown of anyone else's lock. Normal debate release already
carries the RETAINED identity: `new-kimi-lane-home.ps1 -Remove` verifies it,
deletes the home, then releases with it, and `-ResolveOwner` never appears on
that path (`tools/new-kimi-lane-home.ps1:357-375, 476-488`). No release path in
this repo re-resolves.

**Direction, not a decision.** Candidates to weigh in the plan debate: walk up
to the nearest ancestor that is a known long-lived harness process and REFUSE
when none is found, rather than silently returning a wrapper; report the
resolved process NAME so a caller and the doctor can see an intermediate; and
have acquire refuse to record an owner it cannot distinguish from the resolving
shell's own wrapper. Refusing is the safe direction: an owner that cannot be
resolved is not an owner.

**Evidence status, as filed.** The instability itself was the other session's
measurement, not this one's. The parent-only resolution that makes it possible
was measured here.

**CORRECTION, 2026-08-04.** "Reproducing the instability needs a harness that
wraps, and finding one is the first step of this item" was WRONG. It needs one
extra SHELL FRAME. Calling `-ResolveOwner` directly and again through a single
additional PowerShell host returned pid 30944 and pid 4872 - the reported
defect, on this machine, with no wrapping harness anywhere. That is now the
oracle `test_resolve_owner_is_stable_across_an_added_shell_frame`.

**PARTIALLY CLOSED 0.22.0, and the remaining gap is named below.**

**WHAT STAYS OPEN.** Owner resolution recognizes four TRANSPORT names
(`pwsh.exe`, `powershell.exe`, `cmd.exe`, `conhost.exe`) and accepts the
first ancestor outside that set. Amendment 1 of the 0.22.0 plan asked for
the opposite shape - walk to a RECOGNIZED LONG-LIVED ancestor and refuse
when none is found - and the deviation was not recorded until the
cross-vendor round found it (Amendment 2 of that plan). So an EPHEMERAL
wrapper whose executable is named anything else, `node.exe` and
`python.exe` among them, is still accepted as the owner and still exits
when its command does. The stability oracle inserts another copy of the
SAME PowerShell host, so what is established is stability across an added
SHELL frame, not "under any wrapper".

**What is fixed.**

- **The silent half is fixed for shell wrappers.** Acquire refuses an owner
  measured DEAD at its gate, AND re-measures immediately before every record
  write, requiring LIVE there. The gate alone was not enough and the
  cross-vendor round proved it: liveness was measured once, before the
  acquisition loop, so a caller waiting behind a holder could be measured
  LIVE, wait, DIE, and still be written the moment the holder released.
  UNMEASURABLE now survives only where NOTHING is written - the idempotent
  re-entry path, where a matching nonce and retained identity already
  establish ownership. That removes the earlier residual (a running pid with
  WRONG ticks recording when the start-time read failed) rather than carrying
  it.
- **The resolution is stabilised, at a stated cost.** `-ResolveOwner` walks
  past the hosts it is invoked through (`pwsh.exe`, `powershell.exe`,
  `cmd.exe`, `conhost.exe`) and stops at the first ancestor that is not one,
  reporting its NAME. A genuinely long-lived orchestration script running
  inside one of those four is skipped, and the owner resolves to ITS parent -
  a lock that can outlive the debate rather than one that dies inside it. That
  trades this item's VISIBLE half against its SILENT half, deliberately.
- **`ownerName` is an OPTIONAL held-v1 field.** Required would have made every
  pre-upgrade record MALFORMED on the next cache update.
- **Change 1 shipped as a contract region**, `lane-debate-close` in
  `backup-lane.md`, which also states that it is ADVISORY: pinned prose does
  not execute a teardown and nothing detects a debate that finished without
  one.
- **Change 2 shipped in `commands/doctor.md`** with all four undecided rules
  decided: 30 minutes, files under the recorded `debateHome` walked
  recursively with directories excluded, the newest `LastWriteTimeUtc`, and
  TOTAL SILENCE if any part of the walk fails.

**Priority, as filed.** FIRST item of 0.22.0, decided 2026-08-03. It was deliberately NOT
spliced into the in-flight 0.21.0 branch: that plan is frozen and debate-
reviewed, and a fifth item would need its own amendment and review cycle. The
workaround is one release command.

**Priority.** Low. It is a narrower window than the defect 0.22.0 closed, and
