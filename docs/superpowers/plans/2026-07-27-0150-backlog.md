## 1. Replace the pin mechanism — DONE, 0.15.0 and 0.15.1

**Problem.** Contract text is locked by hand-written substring pins. A
pin can stay green while the operative half of the sentence it claims to
lock is deleted.

**Evidence.** Twelve instances across three consecutive cycles: nine in
0.14.2, two in 0.14.3, one in 0.14.4. Two of them appeared inside the fix
for the previous one. In 0.14.4 the pinned string occurred twice in the
same file, so it did not lock even the paragraph's existence.

**Why it is not fixed yet.** Every reviewer seat that looked at it agreed
a follow-on cycle is the wrong vehicle for a mechanism redesign, and that
forcing one in would skip the plan-debate gate.

**Shape of a fix, not decided.** Options include anchored block pins,
a checksum over a marked region, or generating pins from the doc rather
than writing them by hand.

## 2. Make the auto-triage lane fail loudly — DONE, 0.16.0

**Resolved.** `Write(**)` is gone from `--allowedTools`: the CLI rejects it
outright and `Edit(**)` already covered Write, so the rule only ever printed
a warning into a sidecar file nobody read. A test asserted the invalid rule,
which is why it survived; it now asserts the valid one is present and the
invalid one is absent.

A run that does not finish now toasts `AUTO-TRIAGE FAILED` with the cause,
names the remedy for the two recurring classes (out of credits, auth), rides
that reason on the pending entry so a missed toast re-surfaces as a failure
rather than a stale stamp, and copies the runner's own stderr into the
report.

**Sharper than the item assumed.** Every trusted outcome silences the manual
toast, so with auto-triage enabled a manual fallback ALWAYS means the
automation did not finish. There was no innocent case. The plain
"N finding(s)" toast now fires only under the deliberate `-NoAutoTriage`.

Three state-machine scenarios added: one reproduces the 2026-07-21 death
exactly, one proves a missed failure toast re-surfaces, one proves a
verdict-less run is recorded as a generic runner failure rather than
mislabelled. Full suite: ALL SCENARIOS PASS.

**Problem.** The headless drift auto-triage is the unattended safety net.
It can die and leave no signal.

**Evidence.** The 2026-07-21 run exited 1 on `You're out of usage
credits` and sat unnoticed for six days across five releases. Its own
runner also logged a second error: `Write(**) is not matched by file
permission checks, use Edit(**) instead`. Nothing surfaced either until a
human opened the folder.

**Two parts.** Fix the wrong permission rule in the runner's
`--allowed-tools`. Then make a failed triage raise something the user
sees, the same way a finding does.

## 3. Fix the attestation verifier's warning text — DONE, 0.16.0

**Resolved.** The message names the failing field instead of printing all
three values beside a generic requirement, and states that the route note
is an exact token. The pass rule is untouched. Three tests pinned the old
wording; each now asserts the failing field is named and the passing ones
are not, plus a new case where all three fail together.

**Problem.** The pre-push message contradicts itself. It reports the
attestation as PASS, FULL, and route-confirmed, then says one of those is
required.

**Cause.** `tools/verify-attestation.ps1:49` requires `route_note` to
equal the exact token `effective route confirmed`. Any other text fails
the match, and the failure message prints the record's real values, which
read as a pass.

**Confirmed working.** 0.14.4 pushed with the exact token and the lane
reported `attestation: attested:` with no warning. So the rule is right
and only the message is wrong.

## 4. Reduce preflight-3 friction in repos that legitimately carry back-channels

**Problem.** Preflight 3 stops the gate in any repo that carries an
`AGENTS.md` or `.agents/skills/*/SKILL.md`. The stop is correct: codex
ingests `AGENTS.md` as instructions and advertises repo-level skills to
the model, so reviewing over them lets the repo tell the auditor what to
think. But the remediation is hand-built every single time, and the gate
asks for a fresh go-ahead on every run.

**Evidence.** Observed 2026-07-27 in another project, atrocityEssentials:
18 entries blocked the gate, one root `AGENTS.md` plus 17
`.agents/skills/*/SKILL.md` files. The same block had already been
cleared in an earlier session there. The user was offered the same two
options again: build the mirror by hand, or abort the gate.

**Why this matters.** A correct gate that is expensive to satisfy gets
skipped. The abort option routes to a deferred diff gate, which means the
easy path is the one with less verification. That is the wrong gradient.

**What already exists.** `references/backup-lane.md` defines the mirror
and says preflight-3 remediation is performed there, never in the real
tree. It is driver-executed prose, so a human or agent rebuilds it by
hand each run.

**Shape of a fix, not decided.** Candidates, in rough order of appeal:

- Make mirror construction plus remediation a single scripted step, so
  the gate offers one action rather than a procedure.
- Cache the remediated mirror per repo and commit, and rebuild only when
  the tree or the back-channel set changes.
- Record a per-repo standing decision, so a repo whose back-channels are
  known and already remediated does not re-ask on every run.

**Constraint that must survive any fix.** The block itself is not the
problem and must not be softened. The remediation must stay inside the
mirror, and the deletion must still be committed there so the reviewer
cannot read the files. Making it cheaper must not make it optional.

## 5. The rotation claim in backup-lane.md is now false — DONE, 0.16.0

**Resolved.** The false paragraph is replaced with the observed truth and
its on-disk evidence, re-verified 2026-07-28. The residual-gap region
became `rotation-guard-identity`, carrying the rule its own contingency
had promised: capture the log's creation time alongside the byte offset,
and treat any later creation time as rotation whatever the length says.

The region rename is visible in `DECLARED_REGIONS`, and the coverage
checker shipped in 0.15.0 caught all three consequences of the edit before
any review saw it: the renamed region missing from the inventory, the new
region locked by nothing, and the pin still holding the deleted false
claim. Under the old substring pins the middle one would have stayed
green.

**What happened.** On 2026-07-27 the kimi log rotated successfully during
a live backup-lane write-probe in another project. The 0.14.3 rotation
guard fired, detected it, and correctly classed it as a route-attribution
failure. The guard worked on its first real trigger.

**Evidence, verified on disk 2026-07-27:**

- `~/.kimi/logs/kimi.2026-07-25_14-01-45_182023.log`, 459709 bytes,
  created 2026-07-25 14:01:45. This is the renamed old log.
- `~/.kimi/logs/kimi.log`, created 2026-07-27 15:34:43. This is the new
  one. The rename that used to fail now succeeds.

**What is now wrong in the docs.** `references/backup-lane.md` states
that rotation attempts "fire and fail with `PermissionError: [WinError
32]` because the log is still open, so offsets have held by accident
rather than by design". Both halves are false as of this date. The
observation was true when recorded and is no longer true.

**What is now weaker in practice.** The same paragraph admits the size
test is "necessary, not sufficient", because a replacement file that
regrew past a small captured offset would pass it. That was a theoretical
gap while rotation always failed. It is a reachable gap now.

**The fix is already specified by the doc itself.** The residual-gap
paragraph ends: "if rotation ever starts succeeding here, compare file
identity (creation time) too, not just length." That condition has now
occurred. Creation time is usable: the two files above differ by two
days, and the pinned contingency can be implemented as written.

**Scope note.** This item touches the same paragraph as the 0.14.3 pins,
so the pins move with it. That makes it a natural companion to item 1,
whose whole subject is whether a pin still covers what it claims after
the text under it changes.

## 6. The backup lane's evidence rule breaks under concurrent sessions

**What happened.** On 2026-07-27, round 1 of the 0.15.0 plan debate was
discarded unread under the route-attribution rule. Two calls wrote route
lines into one measurement window: this session's dispatch at 16:08:44
(`Created new session 08d55837`) and another project's round 2 at
16:10:22 (`Resuming session 29d43d90`). Full record:
`docs/superpowers/plans/rounds/2026-07-27-contract-coverage/route-attribution-failure-r1.md`

**The rule worked. What it caught was not a threat.** The reply was
almost certainly the right one. Containment held on evidence that does
not depend on the log: no marker file, empty mirror delta, exact tool
allowlist. What failed was attribution, because two calls in one window
make the log unable to say which lines are whose.

**The gap.** `~/.kimi/logs/kimi.log` is user-global. The offset rule
assumes one session at a time on the machine, and says so nowhere. A
driver has no way to know a concurrent session will invalidate its
evidence, and no way to tell a collision from a real misroute after the
fact. The cost is a wasted call and a consent gate for a non-event, and
the predictable response to repeated false alarms is to stop believing
the check.

**Constraint that must survive any fix.** Do not relax the "exactly one"
rule. It is what makes the evidence mean anything. The fix must make
collisions rarer or distinguishable, not tolerated.

**Shape of a fix, not decided.** Candidates:

- Bind the round to the session id the CLI prints, so attribution comes
  from the reply's own identity rather than from position in a shared
  file, with the offset rule kept as the containment check.
- Take a lock for the duration of a dispatch, so two parallax debates on
  one machine serialize instead of colliding.
- Detect the collision before spending the call: capture the offset,
  check for foreign activity since the last round, and warn.
- Ask whether kimi can be pointed at a per-session log file, which would
  remove the shared-stream problem at the root.

**Note on ordering.** Item 1's debate is blocked by this today, so this
item has a live cost right now, not a theoretical one.
