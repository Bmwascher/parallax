**Evidence.** Twelve instances across three consecutive cycles: nine in

## 2. Make the auto-triage lane fail loudly — DONE, 0.16.0

**Resolved.** `Write(**)` is gone from `--allowedTools`: the CLI rejects it
outright and `Edit(**)` already covered Write, so the rule only ever printed
a warning into a sidecar file nobody read. A test asserted the invalid rule,
which is why it survived; it now asserts the valid one is present and the
invalid one is absent.

A run that does not finish now toasts `AUTO-TRIAGE FAILED` with the cause,
names the remedy for the two recurring classes (out of credits, auth), rides
that reason on the pending entry so a missed toast re-surfaces as a failure
rather than a stale stamp, and copies the runner's own stderr into the
report.

**Sharper than the item assumed.** Every trusted outcome silences the manual
toast, so with auto-triage enabled a manual fallback almost always means the
automation did not finish, and the plain "N finding(s)" toast now fires only
under the deliberate `-NoAutoTriage`.

**One innocent case, which an earlier draft of this block denied.** A
`VERDICT: BLOCKED` reply on a CLEAN exit IS a manual fallback, but the agent
read every finding and stopped on purpose: nothing is broken and there is no
runner problem to fix. Recording it as a runner failure would make
`/parallax:drift-triage` report the lane as down, which its own definition of
the `failure` field forbids. It therefore carries no failure reason and gets
its own toast instead. Caught by the whole-branch reviewer, which noticed the
code comment saying "the designed path, not a broken runner" sitting directly
above the line that set the failure anyway.

**The clean exit is load-bearing, and the first fix omitted it.** A crashed
or killed run that happens to print a BLOCKED line before dying is NOT a
deliberate handoff. The first version of this fix keyed on the verdict text
alone, so a nonzero-exit crash was classified as an intentional stop and
recorded an empty failure — telling a triage session the automation finished
on purpose when it had died. The cross-vendor lane found that inside the fix
for the reviewer's finding, which is the same fix-contains-a-defect pattern
this project keeps hitting. BLOCKED now requires `$agentExit -eq 0`, with its
own state-machine scenario.

Three state-machine scenarios added: `credits-death` reproduces the
2026-07-21 death exactly, `failure-resurfaces` proves a missed failure toast
re-surfaces, and `blocked-crash` proves a BLOCKED line on a nonzero exit
reports as a runner failure. The pre-existing `no-verdict` scenario gained an
assertion rather than being added; the backup reviewer lane caught this
enumeration naming it as new. Full suite: ALL SCENARIOS PASS.

**Problem.** The headless drift auto-triage is the unattended safety net.
It can die and leave no signal.

**Evidence.** The 2026-07-21 run exited 1 on `You're out of usage
credits` and sat unnoticed for six days across five releases. Its own
runner also logged a second error: `Write(**) is not matched by file
permission checks, use Edit(**) instead`. Nothing surfaced either until a
human opened the folder.

**Two parts.** Fix the wrong permission rule in the runner's
`--allowed-tools`. Then make a failed triage raise something the user
sees, the same way a finding does.

## 4. Reduce preflight-3 friction in repos that legitimately carry back-channels — DONE, 0.17.0

**Resolved.** `tools/new-review-mirror.ps1` makes construction plus
remediation one command, and `tools/codex-context-probe.ps1` adds the half
this item never asked for: the reviewer's own machine. The block was not
softened. See `docs/superpowers/specs/2026-07-28-reviewer-isolation-design.md`
and item 7 below for what 0.17.0 deliberately left uncovered.

**Problem.** Preflight 3 stops the gate in any repo that carries an
`AGENTS.md` or `.agents/skills/*/SKILL.md`. The stop is correct: codex
ingests `AGENTS.md` as instructions and advertises repo-level skills to
the model, so reviewing over them lets the repo tell the auditor what to
think. But the remediation is hand-built every single time, and the gate
asks for a fresh go-ahead on every run.

**Evidence.** Observed 2026-07-27 in another project, atrocityEssentials:
18 entries blocked the gate, one root `AGENTS.md` plus 17
`.agents/skills/*/SKILL.md` files. The same block had already been
cleared in an earlier session there. The user was offered the same two
options again: build the mirror by hand, or abort the gate.

**Why this matters.** A correct gate that is expensive to satisfy gets
skipped. The abort option routes to a deferred diff gate, which means the
easy path is the one with less verification. That is the wrong gradient.

**What already exists.** `references/backup-lane.md` defines the mirror
and says preflight-3 remediation is performed there, never in the real
tree. It is driver-executed prose, so a human or agent rebuilds it by
hand each run.

**Shape of a fix, not decided.** Candidates, in rough order of appeal:

- Make mirror construction plus remediation a single scripted step, so
  the gate offers one action rather than a procedure.
- Cache the remediated mirror per repo and commit, and rebuild only when
  the tree or the back-channel set changes.
- Record a per-repo standing decision, so a repo whose back-channels are
  known and already remediated does not re-ask on every run.

**Constraint that must survive any fix.** The block itself is not the
problem and must not be softened. The remediation must stay inside the
mirror, and the deletion must still be committed there so the reviewer
cannot read the files. Making it cheaper must not make it optional.

## 6. The backup lane's evidence rule breaks under concurrent sessions — DONE, 0.16.0

**The residual question is ANSWERED YES, 0.18.0.** The last candidate below
asked whether kimi can be pointed at a per-session log file, which would
remove the shared-stream problem at the root. On `kimi-code` it can, and it
does so by default: every session writes its OWN
`sessions/wd_<workspace>/<session-id>/logs/kimi-code.log` and its own
`agents/main/wire.jsonl`. There is no shared stream and nothing to attribute
by position, so the collision this item was raised for cannot occur between
debates at all. That is also why the lane lock was deleted (item 16) — the
window it protected no longer exists. Measured live 2026-07-31; see
`rounds/2026-07-31-kimi-code-swap/kimi-live-debate-record.md`.

**Resolved with both candidate fixes, not one.**

**What blocked the obvious fix.** Candidate 1 said "bind the round to the
session id the CLI prints". The three evidence lines carry NO session id:
their session field is empty, and only later runtime lines are stamped. So
matching an id on the evidence line is impossible.

**What replaced it.** Bind by ORDER. `Created new session: <id>` and
`Resuming session: <id>` DO carry the id and sit immediately before that
session's three lines, so the rule reads only from this round's session
event up to the next event of any id, and requires exactly one of each
inside that block. Foreign session events are ignored rather than counted.
The block's kind is checked too, which catches a resume that silently
started fresh.

**Verified on live data, not reasoned.** A concurrent kimi session was
running in another project during this work. Over a 17583-byte window
holding two foreign startup blocks, the old whole-window rule reported two
of each line and failed; block attribution resolved both sessions to
exactly one of each. That is the 2026-07-27 failure reproduced and then
fixed, on the real log.

**Plus the lock.** Ordering cannot stop parallax colliding with itself, so
`tools/kimi-lane-lock.ps1` serializes this plugin's own dispatches. It is
advisory and age-bounded: no PID is recorded, because the holder is a driver
agent whose shell invocations are each short-lived, so a recorded PID would
read as dead immediately and every lock would look stale. 41 tests cover it,
including that breaking a stale lock is never silent and that a malformed
lock cannot wedge the lane.

**What the lock does and does not guarantee**, narrowed THREE TIMES after the
cross-vendor lane refuted the broader claims this block first made. Each
round's fix contained the next round's defect — three rounds running — so the
wording below is what survived being attacked, not what was drafted:

- The label is the ownership credential. A NONBLANK one is required on
  acquire, so this script never writes a lock without one. It can still read
  a lock written by hand or by an older version, and a release without
  `-Force` refuses those too: an unusable `label` field means no credential
  exists to present. Round 1 claimed "an unlabelled lock cannot exist",
  which was false — `label: 0`, `label: null` and a missing label are all
  falsy, and each was freed by a bare release until round 2.
- Ownership is a case-sensitive STRING MATCH and nothing more. Two callers
  passing the same label are indistinguishable, so either can release the
  other's lane. The contract requires a label unique to the round; the
  script cannot enforce that and does not pretend to.
- The 45-minute staleness threshold is a constant with no override of any
  kind. Two earlier shapes were both lock-stealing: a `-MaxAgeMinutes`
  parameter, so `-Acquire -MaxAgeMinutes 0` broke a fresh lock with no
  `-Force` — demonstrated by this suite's own stale-lock test; then an env
  override honoured "whenever the lock path is redirected", which gated on
  the redirect being PRESENT rather than on it differing from the default.
  Round 1 claimed that seam "cannot be aimed at the real per-user lane".
  It could: setting the redirect to the exact default path stole the real
  lane, reproduced by running it. Tests now backdate their own temporary
  lock instead of asking the script to lower its guard.
- A stamp in the FUTURE used to produce a negative age that never reached the
  stale branch, so the lane stayed busy until the clock caught up and status
  printed "held -360 min" to a human. A future stamp now reads as unusable
  and is breakable.
- Age depends on the INSTANT, not on how the instant was written down. Round
  3 found that it did not: `[datetime]` parsing converted an offset-bearing
  stamp to local time but left a terminal `Z` as UTC, and subtracting two
  `[datetime]` values ignores that difference. On a UTC-05:00 machine a
  CURRENT `Z` stamp therefore read as 300 minutes in the future and was
  broken on sight, while a five-hour-old `Z` stamp read as brand new and held
  the lane past any threshold. Both reproduced by running them. Parsing is
  now offset-aware, and a test asserts the same instant in three
  representations reads the same age.
- A stamp that is not a string — an object, an array, a number — used to
  reach the parser with no matching overload and THROW, which killed the age
  routine before it could return the infinite age it was written to return.
  The lock then read as "held 0 min" and never aged, so the routine that
  exists to stop a malformed lock wedging the lane was itself the wedge, and
  only `-Force` could clear it. Non-string stamps are now unusable and
  breakable, and this block's claim that "a malformed lock cannot wedge the
  lane" is true for the first time.
- An age that cannot be true is described, never printed. Two shapes reached
  a human as measurements: "held -360 min", and "broke a stale lock,
  1.79769313486232E+308 min old" from the sentinel value. Both now read
  "age unusable".
- Residual, real: a LIVE round still running past 45 minutes becomes
  breakable, because nothing checks liveness. Rounds take minutes, so the
  margin is wide, but this is not impossible.
- Residual, documented at the write site: acquire is last-writer-wins, so
  this narrows a minutes-wide race to a milliseconds-wide one rather than
  closing it.

**Residual, pinned in the contract:** a foreign session starting INSIDE this
round's sub-second startup block still truncates it and still fails the
round. Collisions are rare now, not impossible. The "exactly one" rule was
never relaxed, per the item's constraint.

**Original problem, for the record:**

**What happened.** On 2026-07-27, round 1 of the 0.15.0 plan debate was
discarded unread under the route-attribution rule. Two calls wrote route
lines into one measurement window: this session's dispatch at 16:08:44
(`Created new session 08d55837`) and another project's round 2 at
16:10:22 (`Resuming session 29d43d90`). Full record:
`docs/superpowers/plans/rounds/2026-07-27-contract-coverage/route-attribution-failure-r1.md`

**The rule worked. What it caught was not a threat.** The reply was
almost certainly the right one. Containment held on evidence that does
not depend on the log: no marker file, empty mirror delta, exact tool
allowlist. What failed was attribution, because two calls in one window
make the log unable to say which lines are whose.

**The gap.** `~/.kimi/logs/kimi.log` is user-global. The offset rule
assumes one session at a time on the machine, and says so nowhere. A
driver has no way to know a concurrent session will invalidate its
evidence, and no way to tell a collision from a real misroute after the
fact. The cost is a wasted call and a consent gate for a non-event, and
the predictable response to repeated false alarms is to stop believing
the check.

**Constraint that must survive any fix.** Do not relax the "exactly one"
rule. It is what makes the evidence mean anything. The fix must make
collisions rarer or distinguishable, not tolerated.

**Shape of a fix, not decided.** Candidates:

- Bind the round to the session id the CLI prints, so attribution comes
  from the reply's own identity rather than from position in a shared
  file, with the offset rule kept as the containment check.
- Take a lock for the duration of a dispatch, so two parallax debates on
  one machine serialize instead of colliding.
- Detect the collision before spending the call: capture the offset,
  check for foreign activity since the last round, and warn.
- Ask whether kimi can be pointed at a per-session log file, which would
  remove the shared-stream problem at the root.

**Note on ordering.** Item 1's debate is blocked by this today, so this
item has a live cost right now, not a theoretical one.

## 7. The reviewer's TOOL surface is unmeasured

**Problem.** 0.17.0 measures the reviewer's PROMPT: a clean result means
no skill is advertised, no plugin or apps block is present, and nothing
inside the reviewed tree is instructing the reviewer. Tools are not in
the prompt. An MCP server and the memories feature both reach the
reviewer without appearing anywhere the probe can read, so a run can
satisfy every rule above while the auditor holds a code execution tool
and a cross-session memory store.

**Evidence, observed 2026-07-28 during the 0.17.0 behavioral run.** A
review round dispatched with `--sandbox read-only --disable plugins
--disable apps` and the verified skill-disable override logged three
`mcp: node_repl/js started` lines in codex's own transcript. The machine
config carries `[mcp_servers.node_repl]`, `[windows] sandbox = "elevated"`,
`[features] memories = true`, and `[memories] use_memories = true`. The
run also lost two behavioral cases: `diff-mode-spec-fidelity` timed out
with the round still running, and `no-manufactured-objections` kept an
uncited correction.

**Why the 0.17.0 mechanism cannot be reused.** `codex debug prompt-input`
renders prompt text and calls no model, which is what makes it free. It
does not render the tool list: measured the same day, the rendered prompt
mentions neither `node_repl` nor memories anywhere. `codex debug` has only
`models`, `app-server` and `prompt-input`, so there is no free tool-list
view to measure against. A design that verifies a tool removal needs a new
source of evidence, not a second call to this one.

**What is known about the levers, and what is not.** `--disable memories`
is accepted (exit 0), unlike `--disable skills` which errors with
`Unknown feature flag: skills`. `-c mcp_servers={}` parses. NEITHER is
verified to actually remove the tool, because nothing free proves it. Do
not ship either as a control on the strength of parsing alone: that is the
exact false-clean the 0.17.0 probe exists to forbid.

**Constraint that must survive any fix.** Same as 0.17.0's. An unmade or
unreadable measurement is never a clean one, and a lever whose effect is
unverified is a mitigation, not a control.

**Shape of a fix, not decided.** Candidates:

- Find a surface that names the resolved tool list, and measure it the way
  the prompt is measured today.
- Detect the failure after the fact instead: parse the round transcript
  for `mcp:` lines and treat any as a transport failure, which is weaker
  because it spends the call first.
- Route the review through a codex home that carries no MCP servers and no
  memories, which reopens the credential problem 0.17.0 deliberately
  avoided.

## 8. A backup-lane brief can arrive truncated and the round still reads like a review — DONE, 0.18.0

**Resolved by the BRIEF-HASH RULE, not by diagnosing the old transport.**
The lane now hashes the brief BEFORE dispatch — SHA-256 over the brief
canonicalized as UTF-8 with CRLF normalized to LF — and
`tools/read-kimi-round-evidence.ps1` requires the recorded `turn.prompt` to
hash to the same value, over the concatenation of every `input[]` element's
`text` field. A brief that arrives short does not hash to the expected
value, so a truncated round now FAILS as a route-attribution failure instead
of reading like a review. That closes the item's governing constraint: an
unmade measurement is never a clean one.

This is why the brief must be passed INLINE and never planted as a file with
a pointer. A pointer's hash proves the pointer arrived and says nothing
about the brief, so the file-planting workaround round 8 used would defeat
the very rule that closes this item.

**The truncation itself did NOT reproduce on the new client.** Measured
2026-07-31: a 9033-character brief-shaped prompt loaded with shell-special
characters arrived WHOLE — nearly three times the 3225 characters that
truncated on the superseded client. So the mechanism is still undiagnosed on
`kimi-cli`, and deliberately so: the fix does not rest on the diagnosis. The
hash detects a short brief whatever the cause, including a cause that
returns by another path.

**Original problem, for the record:**

**Problem.** The backup lane's round brief is passed as the `-p` argument
to `kimi`. On 0.17.0 panel round 7 the lane received it truncated after
its second line: no head SHA, no task list, no evidence block. The lane
said so itself, under its own Unverified heading, and its reply followed
the STANDING round-1 structure rather than that round's five tasks and
never answered the round's sign-off question.

**Why it matters more than it looks.** The per-round route evidence was
CLEAN: correct model id, correct agent yaml, the five-tool allowlist
exactly, one session block resuming the right id, no log rotation. Every
rule the backup lane has for detecting a bad round passed. The lane
volunteering the truncation is the only reason it was caught. A lane that
did not mention it would have produced a reply about the right tree and
the right diff, and nothing in the evidence would have contradicted it.
That is a round the driver would have counted.

**What is known.** Rounds 5 and 6 delivered the same way and both replies
quoted their briefs back, so the transport is not simply broken. The
round-7 brief carried FEWER shell-special characters than the round-6 one
that arrived whole, so the obvious cause is ruled out rather than
confirmed. Length was 3225 characters against round 6's 3348. The
mechanism is UNDIAGNOSED.

**What was done instead, and what it does not do.** Round 8 planted the
brief as a FILE in the review mirror and passed a one-line prompt telling
the lane to read it. The lane confirmed in its first line that the brief
arrived whole. That avoids the failure; it does not diagnose it, and it
does not detect it if it returns by another path.

**Constraint that must survive any fix.** Same as everywhere else in this
plugin: an unmade measurement is never a clean one. A round whose brief
did not arrive is a transport failure, not a review result, and it must
not be possible for that to be indistinguishable from a real round.

**Shape of a fix, not decided.** Candidates:

- Make the brief file-planted always, and add the file to the per-round
  evidence: its hash before dispatch, and the lane asked to echo the same
  hash back as its first line.
- Put a nonce in the brief and require the reply to carry it, which
  detects truncation anywhere in the chain rather than only at the front.
- Diagnose the `-p` path properly before deciding, since a truncation that
  can happen to a brief can happen to anything else passed the same way.

## 9. Reviewers are the discovery mechanism for mechanical parser faults

**Problem.** 0.17.0 took 12 panel rounds on the primary lane and 8 on the
backup, with 19 checkpoint amendments. Nine defects reached a wrong
measurement or a wrong refusal. Almost all of them were MECHANICAL: which
text a marker was counted in, which string a slice was taken from, which
list a loop walked, whether a quoted example was a container. Each was
found by a model reading code and guessing the shape that would break it,
one shape per round, at two lane calls plus a full gate re-run each time.

**Evidence.** Rounds 3 through 11 each ended with a defect reproduced on
both PowerShell hosts before it was accepted. Five rounds running, the fix
for one round carried the next round's defect, always inside the same
function. The lanes split three times, and every split was settled by
RUNNING the case, never by weighing the reviewers.

**What the reviewers were actually good at.** Design judgment and record
honesty: whether the trade was worth making, whether the accepted-limits
record was complete, whether a comment still described the code. Those are
the findings that could not have come from a test.

**Shape of a fix, not decided.** A generated-shape harness for parser work:
enumerate container arrangements, quoted markers, missing and duplicated
delimiters, nesting, and chunk splits, and assert the invariant that
matters rather than a specific message. The invariant is already written
down: an unmade, failed, or unreadable measurement is never a clean one.

**What this is NOT.** It is not a reason to cut rounds or lanes. The
existing round cap counts CONTESTED exchanges, and nothing in 0.17.0 was
contested; the cap never fired because it was measuring the right thing.
The proposal is to stop spending reviewer rounds on faults a generator
finds in seconds, so the rounds go to the questions only a reviewer can
answer.

## 10. CI does not exercise the probe or the mirror at all — FIX DECIDED, not implemented

**Problem.** `.github/workflows/skill-evals.yml` runs on Linux. The codex
context probe and the review mirror are Windows tools: the probe resolves
the reviewer's global instruction file under `$env:USERPROFILE`, and the
lane lock lives under `$env:LOCALAPPDATA`. Neither variable exists on
Linux, so their 155 test cases are now skipped there. A green CI badge on
this repo says nothing about either script.

**How it was found, and it took two tries.** The 0.17.0 merge turned CI
red: both modules drove `powershell.exe` unconditionally and every case
failed with "No such file or directory", while the Windows suite was
green. The first fix guarded on a PowerShell host being present. That was
not enough - the GitHub runner ships `pwsh` - so the cases then RAN on
Linux and failed on a null `USERPROFILE`. The probe was behaving
correctly in both directions: it refused to publish a measurement it
could not make. The tests had nothing to assert.

**Why the skip is not the fix.** It is honest, and it is a coverage loss
of 155 cases including every rule this plugin's 0.17.0 cycle spent twelve
review rounds establishing. The repo's own standard says an unmade
measurement is never a clean one; a skipped suite that nobody notices is
the same failure wearing a green badge.

**Fix, DECIDED by the user 2026-07-29: add a `windows-latest` job.** It
runs the pytest tier under both `powershell.exe` and `pwsh`, the way the
local gate already does, so the 155 skipped cases are covered by the same
two interpreters that found 0.16.1's lock defect. It costs CI minutes and
it covers exactly what is uncovered. Not yet implemented.

Points the implementer must settle, none of them decided here:

- Whether the Windows job runs the WHOLE pytest tier or only the two
  gated modules. Running everything twice is simpler and slower.
- Whether the existing Linux job keeps running the other three tiers
  alone, or whether skill_lint, skill_scanner and the trigger evals also
  need a Windows pass. They are Python and platform-independent, so the
  default answer is no.
- How `PARALLAX_PS_HOST` is driven on the runner, since the dual-host run
  is two invocations of the same suite with that variable set.

## 12. Investigate a manual "fast" mode when calling the Sol reviewer

**What is already known, so this is not re-checked from scratch.**

reviewer dressed as a faster one is a degraded gate that does not announce

**What to investigate, in order.**

- Whether codex or the account plan exposes a priority or faster service
  tier at all, through `config.toml` keys rather than CLI flags, since the
  flag surface is already known to have none.
- Whether the canonical model has a faster sibling that is still a
  cross-vendor reviewer of equal standing, which is a model-selection
  question for `model-prompting-notes.md`, not a transport one.
- Whether the real latency is the model or the round trip. Rounds in the
  0.17.0 cycle ran five to eight minutes, and no measurement exists of how
  much of that is the reviewer thinking versus the transcript being
  written and read.

**Constraint that must survive any fix.** If the fast path changes what
the reviewer does, it is a DEGRADED verification and the record must say
so, with the class named. If it only changes how fast the same work
returns, it is free to be a plain option. Deciding which of those it is

## 14. The mirror stops on any path containing a space — DONE, shipped 2026-07-31

**Resolved.** Merge `2b3c384`, attested PASS/FULL at head `fed25a4` over
base `f464b00`. The `-z` candidate below was the one chosen; the decoder
candidate was built first, reviewed, and then deleted. Both git pathname
captures now read raw NUL-separated bytes, a guard refuses any pathname
the baseline render cannot reproduce exactly, and the status parse was
rewritten structurally. Plan
`docs/superpowers/plans/2026-07-29-mirror-z-capture.md` (32 amendments,
six plan-debate rounds), design
`docs/superpowers/specs/2026-07-29-mirror-z-capture-design.md`.

Three measured facts from that cycle that this item could not have known:

- Under `-z` the RENAME FIELD ORDER IS INVERTED from the line form. The
  line form is `R  <old> -> <new>`; `-z` emits destination first.
- Of 127 ASCII codes tried, Windows created 87 filenames; git's porcelain
  quotes exactly two of them, the space and 0x7F. 0x7F is creatable on
  Windows, so a "control character" test alone is not enough.
- `core.quotepath=false` suppresses only the non-ASCII display form, not
  space quoting, and under `-z` it is a complete no-op.

The uncommitted concurrent work named below did land, as the decoder
candidate, and was replaced inside the same branch.

**Status when this was written, 2026-07-29 01:38.** A CONCURRENT session,
working in another repo, diagnosed this and has an UNCOMMITTED fix sitting
in this working tree: `tools/new-review-mirror.ps1`, 103 insertions and 18
deletions, not staged, not reviewed. Do not act on this item without first
checking whether that work landed. Do not sweep it into an unrelated
commit; stage by path, never `git add -A`, until it is resolved.

**The bug.** `Test-GitQuotedPath` treated any git-quoted pathname as
unresolvable and stopped the run. Its comment claimed git only quotes
names carrying a double quote, a backslash or a control character. That is
incomplete: git also quotes any path containing a SPACE.

**Confirmed here, not taken on report.** A throwaway repo containing a
directory named `M+ Timer` gives `?? "M+ Timer/"` from
`git status --porcelain` - quoted for the space and nothing else. The same
capture with `-z` returns it verbatim and unquoted.

**Blast radius.** Measured by the other session against a real tree: 5810
of 11874 baseline entries came back quoted, and all but one were plain
ASCII quoted purely for a space. The mirror stops on the first one, so it
never builds. Any WoW project is affected by construction - the reference
convention is `References/M+ Timer`, and the skill's own preflight text
already warns that those paths contain spaces. The 0.17.0 remediation path
is therefore unusable in exactly the repos it was built for.

**Two candidate fixes, and they are not equivalent.**

- `git status --porcelain -z` emits paths verbatim, NUL-terminated, never
  quoted. One flag. It also removes the genuinely awkward case, a
  non-ASCII filename, at the same time. Requires splitting on NUL rather
  than on lines, in every capture, and the rename form `orig -> path`
  changes shape under `-z`.
- Decode the quoted form instead, which is what the uncommitted change in
  the tree appears to do. Keeps line-based parsing and adds a decoder that
  must be exactly right about C-style escapes.

**What review will want to see, whichever is chosen.** This script's
capture path was panel-reviewed across the 0.17.0 cycle and the review
found real defects in it three times. A 100-line change to it is not a
one-flag change in review terms. It needs the same treatment: a case with
a space, a case with a non-ASCII name, a case with a rename, and evidence
the manifest still covers every baseline entry.

**Priority.** Above item 13. A blocked mirror blocks the whole preflight-3
remediation path, which is what 0.17.0 shipped to fix.
