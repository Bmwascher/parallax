# Fable panel lane, round 1: plan review of Option D (completion-coupled dispatch)

Subject: `docs/superpowers/plans/2026-08-31-completion-coupled-dispatch.md` in the frozen copy at commit b5b5716, root `C:/Users/Brandon/AppData/Local/Temp/kerev-pd`. All paths below are relative to that root.

## 1. Do the wrapper composition and the eleven-state classifier close the two false-completion cases?

**Case 1 (interval between the exit-file write and process end): CLOSED by construction, on an unmeasured premise.**

- The epilogue makes classification the wrapper's final in-process act and `exit $LASTEXITCODE` its last statement (plan:124-126). A wrapper suspended, hung in teardown, or killed after writing `exit` never reaches that statement, so the harness task cannot report a successful completion (plan:137-140). This is exactly Sol's case 1 (sol-reply.md:9-13) and the mechanism does address it: the disk state no longer answers alone.
- Two conditions keep this "closed by construction" rather than "closed and proven". First, the closure assumes the harness reports a killed or terminated background task as non-success. That is plausible OS behavior but it is UNMEASURED on the harness surface: Task 4's kill test asserts on the direct process handle (`proc.wait() != 0`, plan:619), and Task 10 measures only the success path (plan:1012-1026). No step ever observes what the harness notification and trailer say for a killed or failed round. Given this cycle's own R9 history, where the harness surface announced a failed round as "completed (exit code 0)" (2026-08-31-dispatch-options-costing.md:186-195), an unprobed assumption about the harness's failure surface is the one kind this plan should not carry. Second, the caller-side rule "the trailer's exit code is the result" is prose at the call sites, not mechanism (plan:848-852); the trailer format itself is admitted unpinned (plan:186-190).

**Case 2 (a later invocation answering with an earlier run's artifacts): NARROWED, not closed.**

- On the intended path it is closed: run B of the same wrapper dies at the create-new claim, the first statement after `$ErrorActionPreference = 'Stop'` (plan:115-116, 130-132), so B's own harness task exits non-zero, and A's output belongs to A's task id, which cannot stand in for B's (POLL-RESULT.md:120-124).
- But the plan deletes `-Poll` on the ground that "a second, post-hoc path to a verdict is the class this cycle keeps reproducing" (plan:80-83), and then ships `-Classify` as a standalone mode with the same inputs (`-DispatchDir`, `-ReceiptPath`, `-ExpectedRound`, plan:77-78) and the same exit map (0 on `reply-present`, plan:161-163). Nothing binds a `-Classify` invocation to the wrapper process that should own it. A caller who runs `-Classify` by hand against a completed round's directory - the exact confusion the old tool documented as its residual (tools/dispatch-detached.ps1:49-57) - gets exit 0 for A's artifacts while believing it is judging B. The only guard is call-site prose: "never re-read the dispatch directory to decide a verdict" (plan:853-855). The old tool's own header condemned exactly this shape: "a safety rule in prose next to a command instead of a mechanism inside it" (tools/dispatch-detached.ps1:69-71). Sol's case 2 is closed for the harness-task path and remains open on the post-hoc `-Classify` path, so the honest word for the case as a whole is narrowed. The plan should at minimum state this residual inside `round-dispatch-states` the way the shipped tool stated its own (tools/dispatch-detached.ps1:49-57), and Task 8's region sketch does not (plan:902-905).

## 2. Attack on the new design

I searched these shapes: kill in Sol's interval (closed, above); rerun of a completed wrapper (claim refuses, plan:130-132); concurrent double start (one winner, plan:594-599); missing reviewed tree (terminating relocation, plan:117, 602-607); torn or unreadable exit file (states 5-6, plan:152-153); stale artifacts inherited across rounds (fresh directory per `-Prepare`, plan:392-394); transcript forgery of the state line (exit code authoritative, plan:196-201); post-hoc `-Classify` misattribution (found, section 1); harness trailer for a killed task (unmeasured, section 1). Two further concrete cases:

- **A lane body that exits the process itself reads as success with no classification ever run.** The body runs verbatim between prologue and epilogue (plan:121). A body containing `exit 0` or `[Environment]::Exit(0)` - a natural slip when adapting the old wrapper shape, whose bodies ended by writing an exit artifact themselves (skills/multi-model-verify/SKILL.md:207, references/backup-lane.md:113) - terminates the wrapper before the epilogue. The harness sees exit 0; no claim of `reply-present` was ever computed; an empty or missing reply reads as a completed round. Under the old design the post-hoc classifier was robust to a misbehaving body (`no-exit-file` at exit 1, tools/dispatch-detached.ps1:631-633); under D the classifier runs in-process and the body can skip it. The plan's constraint "must set `$code` and must write nothing to stdout" (plan:110-111) does not mention this, and no Task 4 test covers it. This is the one direction where D is weaker than C.
- **The epilogue's classify step can be silently bypassed only in the conservative direction** so far as I could construct: an uncaught terminating error in the body or in the classify call kills the wrapper at exit 1. I found no non-body path to a false zero. The vacuous test `test_only_reply_present_exits_zero` (plan:450-452) deserves a mention here: it asserts on the test module's own `STATES` constant, so it can never fail against the tool and locks nothing - it looks like a lock and is not one.

No other false-completion path found among the shapes named above.

## 3. Unbuildable tasks as written

- **Task 4, Step 1, the killed-after-publish test: not buildable as annotated.** The test waits for `dispatch_dir / "exit"` before killing (plan:614). The plan's own note says `exit` is written by the EPILOGUE "when the body returns" (plan:643-646). If the body holds on a barrier, the epilogue has not run, so the `exit` file never appears and `wait_for` cannot return; if the body returns so the epilogue can write `exit`, there is nothing left holding, so the kill has no deterministic interval to land in. The instruction and the test contradict each other. The buildable shapes are: the body writes the `exit` and `reply` files itself and then holds (simulating Sol's interval, with the epilogue's overwrite never reached), or the tool regains an env-gated hold seam in the epilogue - but Task 2 Step 3 deletes `PARALLAX_DISPATCH_HOLD_BEFORE_PUBLISH` (plan:377-380) and nothing replaces it. The plan's flagship test needs its mechanics stated, not gestured at.
- **Task 7, Step 3: an interface no task builds.** All four call sites are told to run "the lane's round-evidence binder, passing `-SealedPriorStateSha256` from the receipt" (plan:850-852). Task 5 adds that parameter to `tools/read-codex-round-evidence.ps1` only (plan:686-689), and the file table names no other binder (plan:205-220). The backup lane has its own binder, `tools/read-kimi-round-evidence.ps1`, with its own mandatory `-PriorState` (tools/read-kimi-round-evidence.ps1:85), and it gains the seal in no task. The two backup-lane call sites cannot be rewritten as instructed.
- **Task 2/3/7: `-WorkdirEvidence` is mandatory in the signature but no call site is told what to pass.** `-Prepare` requires exactly one of `-WorkdirEvidence <literal>` or `-NoWorkdirEvidence` (plan:72-75), yet Task 7's operational shape never mentions either (plan:843-852). Which lane passes which, and what the literal is for the codex lane (whose transcript header carries a `workdir:` line, POLL-RESULT.md:24) versus the kimi lane (whose stderr transcript's contents are unverified here), is left for the engineer to invent.
- Minor: Task 2's test expects the literal "dispatch directory already exists" (plan:337), but the implementation steps produce that condition only via `New-Item -ErrorAction Stop` failing at step 4 (plan:392-394), whose exception text is not that string; an explicit pre-check or message must be added and no step says so. Also Task 3 Step 3's `[Parameter(ValueFromRemainingArguments = $true)]` promotes the script to an advanced script, which changes binding behavior on both hosts; Task 4 has a "verify, do not assume" clause for its exit-code assumption (plan:661-664) and Task 3 needs the same for this one. The many undefined test helpers (`prepare_default`, `build_dispatch_for_state`, `run_wrapper_concurrently`, `kill_tree`, and the rest) are inferable and I do not count them as unbuildable, except where their semantics are the contested part (Task 4's barrier, above).

## 4. The classifier order

The plan's argument for 8-before-9 - a wrong-tree round is worse than a missing reply, and a never-written transcript must not fall through to a reply check (plan:167-169) - proves more than the plan does with it:

- By that same severity logic, `workdir-mismatch` should also precede `exit-nonzero`. As ordered, a round that ran in the live repository AND failed reads as `exit-nonzero`, and the wrong-tree fact - the B1 back-channel event, the one fact that should change operator behavior (2026-08-31-dispatch-invariants.md:52-55) - is invisible. First-match-wins means some fact is always hidden; the plan's own severity argument selects the opposite order from the one it ships.
- Reading a MISSING transcript as `workdir-mismatch` puts a made-sounding claim on an unmade measurement. The state name asserts a mismatch was found; in fact nothing was read. Both land at exit 1, so the direction is conservative and E5 is not violated in the pass/fail sense - but the name misdirects diagnosis (a mismatch indicts the mirror configuration; a missing transcript indicts the wrapper's redirection), and this repo's standing rule is that a contract must describe the mechanism that actually holds (2026-08-31-dispatch-invariants.md:241-242). A twelfth state (`no-transcript`), or region text stating explicitly that `workdir-mismatch` covers the absent-transcript case, would fix the honesty without touching the exit map. The plan folds receipt deviations on the stated ground that "nothing branches differently on any of them" (plan:101-104); here something does branch differently - the human's next act - so the fold is not covered by that principle.

## 8. Pin-rule check on the plan's proposed assertions

Judged against the three clause forms enforced by `evals/multi-model-verify/test_contract_coverage.py`:

- Task 6's three tests (plan:757-768) and Task 7's positive assertions (plan:822-837) are all `"literal" in body` or `body.count("literal") >= 1` - valid pin forms.
- **Not pins, by rule:** `assert "-Poll" not in body` and `assert "3 means \`running\`" not in body` (plan:816-819) are negative membership, explicitly excluded (test_contract_coverage.py:275-287). They are intended as absence checks and are fine as such, but nothing they contain may be counted toward locking any region, and the plan should not describe them as pins.
- **Not a lock of anything:** `test_only_reply_present_exits_zero` (plan:450-452) asserts over the test's own constant; it is not a pin and not a behavioral test either (section 2).
- Task 8 proposes no pin literals at all for the four rewritten regions - Step 3 says "write one pin per region" (plan:916-918) without text. The coverage gate fails red if the engineer gets it wrong, so the direction is safe; but the region sketched at plan:902-905 packs the eleven states, the exit map, and the load-bearing sentence into one region, and a region must fit whole inside a single pin - the plan's own global constraint says a region too long for one pin is two regions (plan:917-918). Expect that split to be forced.
- Behavioral assertions (returncode, endswith) rightly make no pin claim.
